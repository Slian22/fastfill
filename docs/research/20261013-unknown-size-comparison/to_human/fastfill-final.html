FastFill 布局系统交付

输入房间信息（边界、层高、门窗、固定物、房型）和需要的家具清单，输出每件家具的 bbox 尺寸、位置、朝向和支撑关系，可直接导出到 RoomGenBench 生成 3D 场景。下面所有数字都来自实测；未测的格子标“待测”。

交付物：一个系统

flowchart LR
  A[房间 + 家具清单] --> B[尺寸：训练集先验]
  B --> C[布局模型]
  C --> D[S1 确定性修复]
  D -->|通过检查器| F[输出 bbox + 布局]
  D -->|未通过| E[升级：gpt-6.1-sol，再不行用开源 O2]
  E --> F
  1. 尺寸：每类家具用训练集统计的真实尺寸（先验）。LLM 自己给尺寸会系统性偏小，见表 4。
  2. 布局模型：待定 由修订 021 §4 在 R = rpo-dpo1、op-dpo2-e1、27B 学生模型三者中选出并确认。
  3. S1 修复：只沿 XY 平移支撑子树，不改类别、尺寸、朝向和支撑关系；不用 GPU、不用 API。
  4. 升级：只有修复后仍不通过的房间才调用 API；每个请求都保证有输出，不丢房间。

为什么这样做、创新点

  1. 尺寸和摆放分开。尺寸用真实统计，模型只学放在哪。尺寸误差最小，也不会靠缩小家具来过检查；在 RoomGenBench 里生成的是正常大小的家具。
  2. 自修复在线偏好学习。用模型自己的失败样本做 rejected，用同一样本经 S1 修复后的结果做 chosen。dev 上检查器 +0.045、严格准入 +0.08；同样数据只做 SFT 没有这个增益，OptiScene 式合成负例反而变差。
  3. 确定性修复 S1。不花 GPU 和 API，把检查器通过率从约 0.40 提到 0.70（dev 选定，测试集复现）。
  4. 分级升级。本地 8B 模型加修复处理大多数房间，只把失败的房间交给 API，在保持真实尺寸的前提下接近大模型的通过率。比例见表 1。
  5. 评测方法。先查清尺寸混杂（尺寸替换、尺寸固定重新生成），再看网格级碰撞和双评委一致性，避免把“缩小家具”误当成“摆得好”。

做得不好的地方

  • 单次摆放仍明显弱于 gpt-6.1-sol 和 O2（0.52 vs 0.92–0.95）；修复后差距缩到 0.10–0.15。
  • 网格级无碰撞房间 0.548，低于 GT 的 0.797；P 的碰撞 86.5% 在网格层面也确实存在。
  • GPT 评委给我们的分低于 gpt-6.1-sol 和 O6；两位评委都属 GPT-6 家族，同家族偏好没有排除。
  • 从 O2 蒸馏没有成功；单种子、历史测试划分；人工评审（UR）没有做。
