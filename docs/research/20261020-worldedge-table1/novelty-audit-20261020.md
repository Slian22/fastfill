# 可扩展世界与 Agent 任务：反例优先查新与交叉审核

核查截止：2026-10-20。这是定向查新，不是穷尽式系统综述；没有复现外部系统或启动新实验。

**结论：不能声称“别人没有做过可扩展世界＋Agent 执行任务”。这个宽泛方向已有明确先例；连“新增对象可交互＋操作结果持久保存”也已有直接相关工作。** 更窄的物理系统与评测问题仍值得研究，但本次核查没有证明其首创性，本项目目前也没有同协议物理实验支持优势。

本文件修正的是文献覆盖与贡献定位。[进度审计](progress-audit-20261020.md)判断的是本地实现和运行产物，不能用“我们尚无结果”推出“别人尚未做过”。查新后的[大表 v4](table-design-v4.md)已改为两个 panel；结果仍全部为 NE。

> 补充核查：已新增 HappyWorld-Bench、WorldArena、WorldWeave、WRBench，见[来源审核第 4 节](reference-audit-20261020.md#4-补搜到的相关评测与扩展先例)。扩展保持评测和世界质量/任务效用的并列均已有先例，以下旧矩阵并非完整名单。

## 1. 审核方法与判定口径

三个 subagent 分别核查显式具身场景系统、生成式世界模型、开放世界/符号 Agent；第四个独立审稿式交叉审核。主审复核关键反例的方法、实验和官方实现，特别检查“支持某功能”和“实验真正用到该功能”是否被混淆。

| 维度 | 本次问的问题 | 必须区分的情况 |
|---|---|---|
| 扩展 | 同一世界是否在交互过程中加入新空间或新实体？ | 世界集合变大；一次生成大地图；解锁/流式加载已有空间；在线合成新空间；新实体进入可操作状态表 |
| 持久性 | Agent 改过的状态能否约束后续交互？ | 画面相似；作者编辑记录；实例身份；位姿/关节/包含关系；可恢复的物理运行状态 |
| 执行 | 谁真的行动，环境如何响应？ | 人类输入；生成世界的 coding agent；符号工具；键鼠策略；规划器/技能控制；接触物理中的机器人 |
| 联合证据 | 任务成功是否实际跨越扩展事件？ | 分别展示扩展和任务；同一轨迹包含两者；成功因果依赖扩展前后的状态；定量配对对照 |

下表的“未展示/NR”只表示所检查材料未建立该事实，不等于系统不支持。视频、文本与显式物理系统均属于相关工作；不能为了保留“首创”临时把前两类排除。狭义物理轨道可规定新增可访问空间，但须保留对对象级扩展先例的承认。

这些工作足以排除“首次把世界质量和 Agent 任务一起评测”“首次可交互关节世界”“首次执行反馈改场景”等未经限定的主张。它们是候选对照来源，是否能统一控制接口还需适配审查，不能写成已经复现。

## 5. 交叉审核后的主张边界

| 拟用主张 | 审核结论 | 可用表述 |
|---|---|---|
| 首次可扩展 world＋Agent 做任务 | **不能使用**：Genie/SIMA、AgentOdyssey、Minecraft 构成先例 | 说明与已有扩展机制、执行接口、评价对象的差异 |
| 首次把新增对象变得可交互并持久保存改变 | **不能使用**：Oneira 直接重叠 | 明确本项目研究的物理运行状态、空间连接和任务约束 |
| 首次生成可执行世界 / 首次同时评世界和任务 | **不能使用**：多个场景/仿真系统及联合评价已有先例 | 报告统一协议下的效果与成本，不靠表格形式宣称新颖 |
| 同一显式物理世界增建空间，保存历史操作，量化跨扩展任务 | **仍未证明首创**：本轮未建立完全相同的联合实验；查新未穷尽 | 作为待验证的问题与系统设计，不能写成已证实的文献空白 |
| 我们的系统已在上述设置优于已有方法 | **没有本地实验证据** | 物理端到端与配对对照完成前，只写拟议方法/协议 |

可用于当前设计文档的定位：

> 我们研究如何在同一显式物理世界中增量增加任务所需空间，同时保留既有交互状态，并用跨扩展任务衡量这种设计的可靠性与成本。该研究承接可扩展世界、持久状态和具身执行已有工作；其价值需要由统一对照实验建立。

“室内＋显式＋关节＋持久＋扩展”的长限定词本身不是贡献。技术难点应落到可失败、可测量的问题上，例如新增门/房间后的导航连接、重编译时对象/关节状态迁移、旧物体不被新布局破坏、以及成本随增长轮次的变化。是否实际解决这些问题，必须由实现与轨迹证明。

## 6. 对大表和实验的具体修订建议

大表仍保留世界维度与固定执行器维度；新增本文件作为相关工作证据表。14 列得分表不能代替机制比较，也不能把不同论文的成功率直接拼成排行榜。

| 评测层 | 应回答的问题 | 对照与主要读数 |
|---|---|---|
| C：共同有限世界 | 同一任务与控制器下，世界是否可用？ | SceneSmith、EmbodiedGen V2、SceneCode 等经适配后比较；新增审查 EmbodiedSmith、Code2Worlds-2。世界质量＋E2E SR/GC＋生成失败记账 |
| R-grow：真实扩展 | 加入新空间时会不会破坏旧状态，任务还能否完成？ | 扩展深度/规模分层；扩展交付率、旧状态误差、跨扩展任务 SR、增量时延与内存/成本 |
| R-reload：恢复控制 | 故障来自空间增长还是保存/重载？ | 不增建空间的同时间点 reload；与 R-grow 分报，不把重载成功当生成能力 |
| 机制与规模对照 | 效果来自什么，代价如何？ | 完整方法、普通程序化追加、全量重生成＋合格状态恢复、一次预生成＋逐步开放。关闭关键机制仅作消融 |

公平性要求：固定 Agent、观测/动作接口、初始条件、任务约束与失败预算。预生成若提前看到未来请求，应明确为有未来信息的离线参照，且 Agent 不能看到未开放区域；另报告其启动成本。不能故意删除基线的常规保存/恢复能力，也不能把无法适配的系统填零。外部方法不支持 R 时标记不参与该轨道；已承诺支持却生成失败的 episode 才按冻结规则计失败。

Retain 要分开检查对象身份、位姿、关节、包含关系及任务谓词。增长时的物理暂停/继续规则必须固定：正常动力学变化不算状态损坏；比较暂停瞬间的受保护状态与恢复后的物理可行性。模拟器临时索引与接触缓存不应冒充持久语义身份。成功率应按世界聚类做配对置信区间，并保留请求→生成→导入→执行→成功的计数；未知运行不能悄悄改成成功或实测失败。

### 最小判别 episode（拟议，尚未执行）

1. 在 A 房间让固定执行器把指定杯子放入指定抽屉并关上；验证发生了真实动作及状态改变。
2. 此后才增建连接的 B 房间和目标台面，记录扩展前后旧实体与机器人状态。
3. Agent 进入 B，再返回 A，打开同一抽屉并取出同一杯子。
4. 把该杯子送到 B 的指定台面；独立验证器检查动作顺序、身份、物理结果及驻留时间。
5. 用相同任务合同执行预生成、追加、重生成恢复等对照；另跑不增长的重载控制。

这个任务的约束同时依赖扩展前的动作和扩展后的空间，不能通过重新生成一只杯子、提前满足目标或跳过初始操作“成功”。若只能符号修改或使用吸附抓取，必须披露执行抽象，不能标成真实机械臂接触操作。一个成功 episode 仅建立系统可运行性；可靠性结论还需多个世界、扩展轮次和配对重复。

## 7. 检索覆盖与未决项
