# OptiScene 论文与当前 FastFill V1.1 实验对照

核查日期：2026-10-13（Europe/London）。本次为只读审核与已保存结果的重新聚合，没有启动训练、生成或付费评审，也没有修改冻结评分器。

## 结论

本轮冻结的训练与12个诊断评测单元已完成；论文共同基准及完整指标评测尚未完成。当前属于扩展任务上的继续训练与阶段比较，不能称为论文的严格复现。SFT → DPO1 → DPO2 的结构相近；输入尺寸条件、语义推理监督、训练起点、数据、偏好监督和超参数存在实质差异。

可以沿用论文指标建立新的共同评测，其中 OOR 的面积比公式已经实现，并已保存原始与修复后数值。然而，“同公式”不等于“同基准”：当前测试场景、对象范围、输入和后处理不相同，不能把已有数字直接放进论文表格判定胜负。当前的自动零碰撞验收率也不是论文的人工 UR。

OOR不是“发生碰撞的房间比例”、不是交叠物体对的比例，也不是IoU。它不等于我们`rooms_with_main`。代码位于 `fastfill/validate.py:124–130`；该文件SHA256 `ddaff1e5f6dedd949c61267780b92d2a18981926d55939ed038e1e3cdbe17158` 与冻结评分来源一致。四个解析例验证：不重叠=0，两等大框重叠一半=0.25，两框重合=0.5，四框重合=1.5。因此该面积比甚至不保证小于1。论文没有充分说明旋转处理、跨房间聚合和失败处理；本报告只认证公式对应，不认证与作者未公布评分实现逐位一致。

我们的OOR按完成输出的房间求均值，失败另报；自动验收率则包含所有请求、失败计0。不能把失败OOR强行置0，否则会奖励生成失败。当前`size_iou_3d`只比较尺寸，忽略位置、朝向，不是完整布局的3D框IoU，也不是论文主指标。

当前碰撞检查考虑高度、支撑关系并区分main/tuck/contained；OOR本身没有这些豁免。当前自动valid也不包含“零碰撞”要求。修复后的`zero_collision_accepted`另外检查main/severe为零，仍不等于人工认可、网格无碰撞或功能/美学合格。

## 当前尚未解决的公平性问题

1. **测试身份与训练重叠**：我们的数据使用独立分组划分；尚无证据证明当前测试ID等于论文676个ID，也尚未完成这些ID与我们训练、偏好对、warm-start历史训练的交集审计。不能把“本轮train/test不重叠”升级成“所有预训练阶段均未见测试场景”。
2. **输入含目标派生信息**：既有审计已确认对象顺序/编号继承真实尺寸与姿态的排序信息，当前报告固定为diagnostic_only。论文已知尺寸任务允许使用输入尺寸；但目标位置/姿态不能用于构造请求顺序。修正输入合同需要另立版本，不能悄悄更改本轮评分。
3. **任务和后处理不同**：论文固定检索资产的尺寸；当前预测尺寸，还会用程序修复支撑、边界、尺寸和碰撞。模型直接输出与完整系统输出应分别报告；当前修复器的收益不能归给纯模型，也不能假定作者使用了同样修复器。
4. **继承模型来源**：本次重新哈希服务器四个基座权重分片，均匹配 `liantian/OptiScene-Qwen-8B-Final` 的HF revision `e554a8c835cb4b212b0af75a5f9adc969ef11194`，下载缓存记录也一致；这证明下载来源，但该revision没有模型卡，未建立其上游训练历史或与作者论文最终checkpoint的关系。严格复现需要原始Qwen、数据与每阶段训练来源；方法比较可保留warm start，但须披露并控制测试暴露。

## 原论文/公开实现仍需澄清的地方

官方README目前示例使用Qwen2.5-7B-Instruct、SFT 1 epoch、DPO 10 epochs、DPO lr=5e-6、r=32/alpha=16；上传论文第7页是Qwen3-8B、SFT10/DPO5 epochs、DPO lr=5e-7、r=16/alpha=32。README也把权重链接标为Coming Soon。复现时不能默认为README配置就是论文实验配置。

本地官方源码绑定 `https://github.com/PolySummit/OptiScene.git` commit `409f1317e1a8afe852f4cdc99dfefaed30aeb425`。其main入口仅SFT/DPO/merge/inference，没有论文OOR/FID/GPT/UR/编辑/导航benchmark评分器，也没有676测试ID清单。训练JSON与Git-LFS指针一致；SFT公开文件为12,253行/11,957独立UID，DPO1为7,951/1,989，DPO2为8,410/2,134。数据包记录数与论文过滤后的16,666也不相同，不能直接把公开全量文件当作论文最终划分。

原公开trainer使用行级80/20切分。专项只在内存中复现该切分，发现validation中与train共享相同instruction+input+chosen的比例：SFT111/2,451，DPO1 1,591/1,591，DPO2 1,668/1,682。DPO负例可以不同；这说明其内部validation不独立于训练场景，不证明论文另设test泄漏，也不是我们当前分组划分的发现。原始UID与HF导出UID采用不同命名规则，零字面交集也不足以证明无重复。

渲染侧还有本地数据问题：缺94个引用资产目录，影响182场景/216实例；一个bedroom-0资产bbox声明的轴序与实际mesh包围盒不符。它们需要在渲染基准前处理，但这里不据此推断整个上游资产包不完整。详情和复现脚本见 `audit-evidence/optiscene-original-audit-20261013.json` 与同名`.py`。

论文§4.2称每类50场景，表3却包含75%、55%、25%、35%。这些数值不能直接还原为每类50次、未经取整的单次二元成功率；可能涉及粗粒度取整、重复平均、不同分母或报告误差，论文未交代，需原始计数与聚合规则澄清。表6的33%UR同样缺乏可还原的分母。本项是需要澄清的评测细节，不是对原始数据造假的判断。DPO的5 epochs阶段分配、表5的NE向上箭头与距离定义、FID配置和GPT评审模型快照也需澄清。

## 可执行的对标路径

1. **先冻结共同评测合同**：锁定官方676测试ID或另立双方未见的新留出集，核对训练/偏好/warm-start重叠；明确已知资产尺寸任务与联合尺寸任务。训练超参数不同并不禁止方法比较，但输入信息和测试条件必须可比。
2. **复用已保存结果做诊断，新增共同条件的生成才算benchmark**：现有原始/修复OOR和房型分层已经提取。在同一冻结合同上重新运行我们与可验证的OptiScene/选定基线，保存逐场景输出；新留出集不能沿用论文表格数值作为对照。作者权重身份无法验证时，应标注方法重实现或其他基线。不能通过改列名、换分母、把预测尺寸事后覆盖为GT，就宣称复现论文。
3. **补齐缺失评价**：同资产/相机/渲染与特征实现的FID；表9对应的固定GPT评审配置；盲评、打乱方法身份的5人多数票UR。实际编辑和导航另设数据，不混进静态布局成功率。
4. **按目标决定是否重训**：仅建立公平新基准时可先复用现有checkpoint并披露限制；若要严格复现论文训练，须从可验证的Qwen起点、论文数据和reasoning监督重新建立协议。当前没有据此自动启动新训练。

优先交付应为固定ID和输入合同的评测清单；在这些尚未确定前，继续训练不会自动产生可与论文表格比较的结论。
